# Known limitations

- Comment detection is lexical. Strings hide comment markers only on a single line and only in the languages listed under [Strings](code-tags.md#strings): a multi-line string (triple quotes, raw strings, heredocs, multi-line template literals) is followed on its opening line only, and in a language without a string family - shell, YAML, Perl, Tcl, LaTeX, XML/HTML markup, JSX/TSX, Less, Emacs Lisp, EDN - a marker inside a string, or inside an unquoted URL, still opens a comment and can define a phantom item. Literal forms beyond the plain ones (raw strings, C# verbatim strings, Ruby `?c`, regular-expression literals, MySQL backslash escapes) are not recognized either.
- Input paths are compared exactly and case-sensitively, after only lexical normalization (`.` and `..` segments, separators): no case folding, no symlink resolution. On a case-insensitive file system, or through a symlink, the same file reached under two spellings (e.g. `docs/spec.md` and `DOCS/spec.md`) is read twice, and its items are reported as duplicates (see [Text handling](text-handling.md#paths)).
- The scanner does not read Git's index. A tracked or staged file matching an ignore rule is excluded during directory scanning. Supply that file explicitly to include it. `git ls-files --cached` would resolve this, but flashtrace deliberately does not invoke a Git executable: one found via `PATH` could be a planted malicious binary running with flashtrace's privileges.
- A `core.excludesFile` path containing `~` anywhere but a leading `~/` is misread: the file walker (the `ignore` crate) replaces every `~` with the home directory, unlike Git, so that global ignore file is not found and its rules do not apply. This affects Windows 8.3 short paths such as `C:/Users/RUNNER~1/...`. Write the path in its long form or start it with `~/`. An upstream fix is pending: [BurntSushi/ripgrep#3592](https://github.com/BurntSushi/ripgrep/pull/3592).
